# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

The git root holds IntelliJ `.idea/` config; the actual Maven project lives in the `sale-management/` subdirectory. Run all Maven commands from there.

## Commands

Spring Boot 4.1.1, Java 21, Maven wrapper (use `mvnw.cmd` on Windows cmd/PowerShell, `./mvnw` in Git Bash).

```bash
cd sale-management
./mvnw compile                       # build
./mvnw spring-boot:run               # run (needs PostgreSQL and JWT_SECRET, see below)
./mvnw test                          # all tests
./mvnw test -Dtest=SaleManagementApplicationTests             # single class
./mvnw test -Dtest=SaleManagementApplicationTests#contextLoads # single method
```

No linter/formatter is configured.

## External dependencies

- **`org.module:publish-service:0.0.1-SNAPSHOT`** — a separate, in-house "core" library that is not in this repo and not on Maven Central. It must already be installed in the local `~/.m2` repository (built/installed from its own project) or the build fails. `SaleManagementApplication` adds `org.module.publish_service` to `scanBasePackages` so its beans are picked up.
- **PostgreSQL** at `localhost:5432/sale-mgmt` (credentials in `src/main/resources/application.properties`). The schema is owned by **Flyway** (`src/main/resources/db/migration`, `V<n>__name.sql`); Hibernate runs with `ddl-auto=validate`, so every entity change needs a new migration — never edit an applied one. `baseline-on-migrate` lets the pre-Flyway dev DB start at V1.
- **Tests**: `RestaurantSchemaTests` uses the `test` profile (`src/test/resources/application-test.properties`) against a separate `sale-mgmt-test` database that Flyway builds from V1; `SaleManagementApplicationTests` uses the dev DB. No Docker/Testcontainers.

## Architecture

Code is organized by feature module under `org.commerce.sale_management.module.<name>_service`, each with its own `constant/RouteConst`, `controller`, `dto`, `model`, `repository`, `request`, `service` (+ `service/impl`), and `specification` (+ `specification/filter`). `module/folder_template` is an empty skeleton to copy when starting a new module. `user_service` has full CRUD; `menu_service`, `table_service`, `order_service` and `payment_service` currently have entities, enums (`constant/`) and repositories only. `AGENTS.md` holds the restaurant-app requirements and phase plan.

Most CRUD plumbing comes from `publish-service` base types; a feature is wired by plugging its types into these generics:

- **Entity** extends `BasePrimaryIdEntity` (provides id, audit fields like `createdAt`, and `isActivate`). Deletion is soft: set `isActivate = false` (see `UserServiceImpl.disabled`).
- **Repository** extends `BaseCombineRepositorySpecification<Entity, IdType>` (JPA repo + specification executor).
- **Filter** extends `BaseInternalRequestFilter` (provides e.g. `search`); bound from query params via `@ModelAttribute`.
- **Specification** extends `BaseInternalSpecification<Entity, Filter>` and overrides `addPredicates(...)`, appending to the inherited `predicates` list and reading `queryFilters`.
- **Service impl** extends the local `BaseInternalAppService<Entity, Id, Repo, Filter, Spec>` (a thin subclass of `BaseInternalServiceImpl` that supplies `currentUser()`), and implements a feature interface. Inherited helpers include `findAll(pageable)`, `findAllSpePageFetch(filter, pageable)`, `findAllView(DtoClass)`, `findOneThrow(id)`, `save`, `update`.

Conventions:
- Request/DTO payloads are grouped as static nested classes in one holder class with lowercase names (`UserRequest.save`, `UserRequest.update extends save`, `UserDTO.view`). `findAllView` maps entities into DTOs via a DTO constructor.
- Routes are string constants in the module's `RouteConst` (e.g. `USER = "api/user"`).
- Field names in criteria/sort use Hibernate JPA static metamodel classes (`User_.USERNAME`, `BaseEntity_.CREATED_AT`), generated by `hibernate-processor`.
- Lombok throughout (`@Getter/@Setter/@Builder`); entities use `@JsonManagedReference`/`@JsonBackReference` for bidirectional relations.

## Security

Stateless JWT (HS256) via Spring's OAuth2 resource server (`security/`):
- `POST /api/auth/login` → `{accessToken, tokenType, expiresIn, username, role}`; send `Authorization: Bearer <token>`. `GET /api/auth/me` returns the caller.
- Env vars: `JWT_SECRET` (required, ≥ 32 bytes — startup fails otherwise); `BOOTSTRAP_ADMIN_USERNAME` / `BOOTSTRAP_ADMIN_PASSWORD` create the first ADMIN at startup when none exists. The `test` profile has its own test-only secret.
- The token's `role` claim becomes `ROLE_<UserRole>`; `/api/user/**` is ADMIN-only, everything else requires authentication. `@EnableMethodSecurity` is on for per-endpoint `@PreAuthorize`.
- `BaseInternalAppService.currentUser()` returns the caller's username (audit `createdBy`/`modifiedBy`); use `CurrentUser.reference()` for user foreign keys (`created_by_user_id`, `received_by`, `changed_by`).
